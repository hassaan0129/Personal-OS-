# Mobile local command engine (Phase 1D-A through 1D-C5)

Phase 1D-A adds the mobile-only foundation for transactional optimistic commands. Phase 1D-B adds isolated transport and acknowledgement reconciliation for task creation. Phase 1D-B2 connects task creation and completion to the existing Today screen. Phase 1D-B3 adds foreground recovery, manual retry/refresh controls, and read-only safe issue details. Phase 1D-C1 connects task editing. Phase 1D-C2 connects task reopening. Phase 1D-C3 connects cancellation for active tasks using the existing structured reason contract. Phase 1D-C4 connects rescheduling using the existing `task.reschedule` lifecycle. Phase 1D-C5 connects ordering through the existing numeric `task.reorder` lifecycle; neither slice is broad offline Planner Mode support.

`expo-sqlite` owns one local database with WAL and foreign keys enabled. Migrations use `PRAGMA user_version` inside an exclusive transaction; the schema version advances only after each migration succeeds, so a failed or interrupted startup retries safely. Normal startup never resets product data.

All local records use `user_id`. The current schema contains:

- `local_today_snapshots`: validated user-scoped Today projection.
- `outbox_operations`: validated command envelope, stable operation ID, expected server revision, deterministic `local_sequence`, target ID, dependency operation ID, attempts, retry state, and safe error message/code.
- `temporary_task_mappings`: local temporary task ID, server task ID once known, and its create operation ID.
- `sync_state` and `sync_conflicts`: reserved user-scoped hydration and explicit-conflict metadata.

`LocalCommandEngine` validates every command through the shared schemas, reads the local snapshot, applies the optimistic projection, registers temporary task identity when needed, and inserts the outbox record in one repository transaction. It supports wake, sleep, previous-Life-Day repair, task create/edit/reorder/Top 3/complete/reopen/reschedule/cancel, and unfinished-task resolution. It rejects missing snapshots, invalid transitions, duplicate completion, a fourth active Top 3 selection, and unresolved task closure before a remote request is attempted.

The backend's `command_create_task` RPC generates the authoritative task ID and does not accept a client task ID. Phase 1D-A therefore uses a UUID temporary task ID locally and records its create operation. Phase 1D-B persists the accepted server task ID in the user-scoped mapping, replaces the temporary task ID and authoritative revision in the cached Today snapshot, rewrites each pending/retryable dependent task command's target and validated `payload.taskId`, marks creation acknowledged, and stores a returned sync cursor. If one or more local edits already predicted later revisions, acknowledgement retains the higher local revision so a subsequent edit does not use a stale base revision. The whole acknowledgement runs in one exclusive SQLite transaction.

An operation is eligible only when it belongs to the authenticated user, is pending or retryable and due, and has no dependency or an acknowledged same-user dependency. A rejected, conflicted, missing, or otherwise unresolved prerequisite cannot release its dependents. Claiming an operation and moving it to `processing` occur in the same exclusive transaction. Stable operation IDs are retained for every retry. If Supabase commits but local acknowledgement persistence fails, the operation is retried; the server's `duplicate_accepted` response safely repeats reconciliation. A different server ID for an existing temporary-task mapping becomes an explicit local conflict rather than overwriting data.

The processor uses only the existing typed Life Day and task command adapters. It does not perform direct table writes, use privileged keys, add a pull/snapshot protocol, or automatically rebase expected revisions. A stale expected revision remains an explicit conflict. Temporary Life Day mapping and offline wake/sleep/repair are intentionally out of scope.

After authentication, the mobile screen initializes the user-scoped store, renders the cached Today snapshot, and then drains the outbox whenever Expo Network reports a reachable connection. On a background/inactive-to-active transition it first recovers stranded `processing` operations, then makes one bounded drain attempt. A controller-owned per-user gate coalesces network, foreground, and manual actions so they cannot run processors concurrently. Sign-out and session-effect cleanup stop the session processor and remove AppState listeners.

Manual retry only makes the signed-in user's `retry_scheduled` rows due; it never changes operation IDs, conflicts, permanent rejections, or dependency rules. Manual refresh uses the existing typed Today adapter and a SQLite transaction to merge the authoritative snapshot: a locally pending/retrying/conflicted/rejected task projection is retained while all other task data is authoritative. This deliberately prevents a refresh from erasing an offline-created temporary task or a pending local completion. Read-only issue details expose only command type, safe code/message, classification, timing/attempt metadata, and prerequisite blocking; they never expose command payloads, raw responses, tokens, or database errors.

Local task creation, editing, ordering, completion, reopening, cancellation, and rescheduling are wired in this slice. An edit immediately updates title, description, priority, estimate, and scheduled/flexible fields in the cached snapshot, then records a validated `task.update` command with the displayed task revision. Completing and reopening a task both advance the predicted cached revision, so a reopen waits behind its preceding completion (and any create/edit command) with the revision the server should have after that predecessor succeeds. Ordering mirrors `command_reorder_task`: planned, in-progress, and overdue tasks use the existing numeric position model; Move Up/Move Down derives a fractional position from the adjacent displayed task, advances the predicted revision, queues after prior same-task operations, and sorts local and merged snapshots by position, creation time, then ID. Cancellation is limited locally to planned or in-progress tasks. It immediately marks the cached task cancelled, clears Top 3, advances the predicted revision, and queues its validated `task.cancel` envelope after all earlier task operations. Rescheduling mirrors `command_reschedule_task`: it accepts only planned or overdue tasks, requires a non-null UTC instant and valid IANA timezone, does not move the task between Life Days, restores an overdue task to planned, advances the predicted revision, and queues its validated `task.reschedule` envelope after all earlier task operations. Existing reason codes (`user_rescheduled`, `capacity_limit`, `external_change`, `no_longer_relevant`, `duplicate`, `other`) are preserved and `other` requires a trimmed note; the processor never rewrites a reason, timestamp, timezone, or stale expected revision. A remote revision mismatch becomes a safe local conflict and keeps the intended cached task projection visible. Wake, sleep, repair, Top 3, and unfinished-task resolution remain online-only. There is no cursor pull, realtime subscription, automatic revision rebase, or conflict overwrite action. Sign-out clears the signed-in user's local snapshots, outbox records, mappings, sync state, and conflicts. The focused test harness uses injected repositories and transport; native Expo SQLite migration testing remains a future manual/device validation item.

SQLite is not encrypted at rest. It must not contain service-role credentials, secrets, or journal content. Supabase access tokens continue to be managed only by the existing SecureStore-backed authentication client.
